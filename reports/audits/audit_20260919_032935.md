- 暗黙の列挙子値/順序が固定されていない
  - なぜ問題か: Unity は enum を整数でシリアライズするため、将来の挿入・並べ替えで既存アセット/セーブデータが意図せず変化する。ネットワーク/保存形式でも互換性が壊れる。
  - どう直すか: すべての列挙子に明示的な数値を割り当て、順序を変えない運用を明文化。不要値は削除せず [Obsolete] で予約し再利用しない。ABI 変更時はマイグレーションスクリプトを用意。

- default(GamePhase) が Ready になる設計
  - なぜ問題か: 未初期化/破損入力/型のデフォルトが意図せず Ready と解釈され、バグを隠す。「見ていないのに緑」の温床。
  - どう直すか: Unknown/None=0 を追加し、Ready=1, Playing=2, GameOver=3 のように明示値を設定。Unknown を受け取ったらエラー/フォールバックするガードを実装・テスト。

- 無効値の受入れに対する防御とテストが想定されていない
  - なぜ問題か: 外部入力/破損データ/将来の拡張で定義外の整数が入るとサイレントに 0（=Ready）や既定分岐に落ち得る。
  - どう直すか: 入口で Enum.IsDefined もしくは範囲チェック、switch の default で明示エラー。負値、巨大値、未知値のUT/ITを追加。

- 数値順序に依存したロジックの潜在リスク
  - なぜ問題か: 比較（<=, >=）やインクリメントで遷移を表現している箇所があると、列挙子の追加で壊れるがテストが気づかない。
  - どう直すか: 数値順序に依存せず、明示的な状態遷移表/関数で判定。順序に依存しないことを静的解析ルール/レビュー基準にする。回帰UTを用意。

- 仕様（IF-09/ST-08）とオラクルの乖離リスク
  - なぜ問題か: コメントに参照はあるが、機械判定可能な遷移規則（例: Ready→Playing→GameOver 以外は無効）がコード/テストに埋まっていないと、誤写したテストに実装が忠実になる。
  - どう直すか: 遷移許可関数とその網羅UT（各状態×全入力の真偽表）を用意。曖昧語は禁止し、テスト名に IF-09/ST-08 の要件IDを埋め込む。

- Unity 固有の破壊経路（列挙子の追加・削除・並べ替え）
  - なぜ問題か: 既存シーン/Prefab/ScriptableObject の enum フィールドが別の値に化ける。検出されず本番で挙動が変わる。
  - どう直すか: 列挙子値を固定化（上記）。変更時はプロジェクト全体で該当型のシリアライズ使用箇所を検索し、検体アセットを実機で開き差分検証。Editor スモークテストに含める。

- 型/名前空間の変更による参照断裂の未対策
  - なぜ問題か: asmdef や名前空間移動で Editor/Runtime 間の参照が壊れると、ビルドのみ失敗や実行時型解決失敗が起きるが、終了コードだけで見落とす恐れ。
  - どう直すか: Game.Core を Runtime asmdef に配置し、Editor からの参照方向のみ許可。名前空間/アセンブリ変更は CI で Editor/PlayMode/ビルドの三系統を回して検知。

- テストの「見ていないのに緑」検出器がない
  - なぜ問題か: このファイル自体はロジックが薄く、テストがゼロでも失敗しない構成になりやすい。skip が分母から外れて緑化する恐れ。
  - どう直すか: 変異（列挙子順序のシャッフル/数値変更）で少なくとも1テストが落ちることを確認。カバレッジにこのファイルを含め、skip を分母に入れる設定にする。

- シリアライズ互換性（ワイヤ表現）の明文化不足
  - なぜ問題か: JSON/MessagePack 等で名前ベース→名前変更で後方互換が壊れる、数値ベース→並び替えで壊れる。
  - どう直すか: ワイヤは数値固定を使い、名前は自由に変更可能に。あるいは名前固定＋ rename 禁止を規約化。互換性テストをCIに追加。

  - なぜ問題か: 列挙子削除で既存データが未定義値になる。実行時に Ready(0) へ丸められるとバグを隠す。
